## 报告

## 范围

运行时归档验证、路径遍历、PR 源码构建来源、进程生命周期、本地端点暴露、安装程序完整性、Tauri 能力。

## 本地认证

桌面管理的模型进程绑定到 `127.0.0.1` 的内部端口，每次启动通过临时 `--api-key-file` 传递 bearer token。临时文件会在启动后删除，Token 会在模型停止时清除。独立控制的外部 API 同样绑定到 `127.0.0.1`，使用单独的内存密钥；模型切换或 API 停止、启动不会更换该密钥，应用退出后密钥才会失效。同一 Windows 用户权限运行的进程仍可能检查或操作这些服务，这是预期行为。请勿共享端点或密钥。

无头 CLI 的 `server start` 模式不同：它会有意使用 `--no-api-key`，并依赖 `127.0.0.1` 绑定。任何能访问该端口的本地进程都可以调用它，因此只能在可信计算机上使用，不要将端口暴露或转发到外部。

API 服务器同样仅限本地使用。MCP 服务器是以用户权限启动的第三方可执行文件；只添加可信程序，并按照配置的批准策略检查工具调用。

MCP 服务器首次启动需要原生 OS 批准，批准与命令、参数、按白名单继承的环境及工作目录绑定。任一执行输入发生变化都会再次提示。批准指纹保存在由 Rust 管理的独立数据文件 `mcp-launch-approvals.json` 中，而不是可编辑的服务器列表中；工具调用批准仍单独处理。

## 运行时 help 执行

所有桌面 help IPC 路径都要求对准确的可执行文件路径、参数、实际工作目录和环境进行原生批准，已安装的运行时和已注册的产物也不例外。执行输入不变时可复用已保存的批准。被拒绝的请求不会启动 help 进程；实际执行的命令与批准界面展示的命令一致。

Help 是代码执行，不是沙箱。外部 Python 为兼容性保留现有的包搜索行为，因此工作目录中的模块可能替代已安装的包运行。只批准可信的运行时和目录。批准指纹不保证目录内容保持不变。直接运行 CLI 时仍采用信任本地调用者的模型。

取消及新请求替换不仅覆盖 help 执行，也覆盖等待原生批准的阶段。已撤回的请求无法保存迟到的批准或启动 help 子进程。保存批准时使用与取消操作相同的所有权锁，确认请求仍然有效后才写入。

## 网络重定向

运行时的 GitHub 和 Hugging Face 请求会在每次重定向时要求 HTTPS 及可信服务主机，最多允许 10 跳。GitHub 元数据使用 GitHub 主机白名单；运行时及验证模型传输使用可信下载主机。最终响应 URL 也会检查；即使起始 URL 获准，也不能经过不可信主机或降级到 HTTP。

## 预构建 PR 产物

便携式 ZIP 和工作流发布的 CPU 产物会验证 platform/arch/backend/build-id、GitHub 资产 SHA-256、文件级清单 SHA-256、嵌入的 PR 仓库/提交、必需可执行文件和正常预检。接收方 PC 无需 CMake/编译器/SDK，但 GPU 运行时需要兼容 GPU 驱动。工作流默认仅发布 CPU，GPU 需从带 SDK 的机器导出。

## 从源码构建 PR

以用户权限编译第三方代码。下载前显示来源（标题/作者/仓库/分支/提交/状态）并固定到该提交 — 如果 head 移动则拒绝。通过提交固定的 HTTPS 获取 PR 源码归档并检查预期的提交目录；GitHub 不会为该源码归档发布可信摘要，因此存储的 SHA-256 为本地审计记录。发布安装程序会在可用时使用 GitHub 资产摘要，否则使用 `checksums.txt` 作为备用。校验和只能确认文件完整性，不能证明发布者身份。构建限制在归档内（BoringSSL/libcurl/OpenSSL 关闭），需两步确认，所有 PR 状态均会明示。支持的后端：`cpu` `vulkan` `cuda` `rocm`（拒绝 SYCL/OpenVINO）。

## 子进程环境

`llama-server`、`llama-bench` 和 CMake 构建在清空的 env + 按平台的显式白名单下运行。代理/TLS 变量为企业构建而传递，敏感信息（`GITHUB_TOKEN`、`*_TOKEN`、`*_PASSWORD`、`SSH_AUTH_SOCK` 等）会被排除。Git 凭证助手已禁用。

## 支持的版本

最新版本和 `main` 会获得修复。旧版本可能需要升级。

## 隐私

网络请求、本地数据、凭据和第三方服务的处理请参阅[隐私政策](privacy.md)。

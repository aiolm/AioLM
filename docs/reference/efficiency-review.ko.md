# 프로젝트 효율 검토 기록

전체 코드의 반복 검토와 개선을 진행 중이다. 아래 결과는 완료한 항목의 근거이며, 프로젝트 전체의 검토나 최적화가 끝났다는 판정이 아니다. 시작 소스는 `08c0916`이다.

## 1차 프런트엔드 개선

| 항목 | 확인한 비용과 변경 | 검증 |
|---|---|---|
| F01 모델 설정의 프로필 처리 | 프로필 65개를 둔 상태에서 옵션 하나를 입력하면 전체 라이브러리를 71번 복사했다. 각 행의 기본 프로필 보호 판정이 같은 정규화를 반복했고, 초기 설정·저장 대상도 다시 계산했다. 라이브러리·엔진·언어가 바뀔 때만 목록과 보호 정보를 계산하고 초기 복사를 지연했다. 같은 입력의 전체 라이브러리 복사는 0회다. | `ModelSettingsDialog.test.tsx`의 합성 다수 프로필 검사. 기존 선택·엔진별 기본값·삭제 보호·이름 변경·저장·재시도 검사도 유지한다. 구현 커밋 `57cf13e`. |
| F02 실행 인자 변환 | 인자마다 전체 옵션 목록을 다시 찾던 작업을 한 번의 호출 안에서 만든 별칭 인덱스로 바꿨다. 단일 인자 경로는 목록 복사를 만들지 않는다. 중복 별칭은 처음 나온 정의를 유지하며, 다음 호출은 바뀐 도움말을 다시 읽는다. | 기존 argv 변환·관리 옵션 거부·음수·반복 인자·Unicode/공백 경로 검사와 별칭 충돌·변경 검사. 구현 커밋 `84486ef`. |

F02 합성 비교는 같은 Node `22.23.2`에서 파싱과 표시 변환을 왕복하고 결과 일치를 검사했다. 각 조건은 워밍업 후 7회 측정한 중앙값이다. 옵션/인자 수가 다른 조건을 서로 비교하지 않는다.

| 옵션 수 / 입력 줄 수 | 수정 전 | 수정 후 |
|---|---:|---:|
| 255 / 1 | 0.01145 ms | 0.01040 ms |
| 255 / 40 | 0.31542 ms | 0.04639 ms |
| 1,000 / 1,000 | 20.37626 ms | 0.64304 ms |

이는 합성 변환 함수의 측정이며 GUI 전체 지연 시간이나 실제 엔진 추론 속도를 뜻하지 않는다. 실행 환경과 다른 작업의 부하에 따라 절대 시간은 달라진다. F01은 시간 임계치 대신 실제 전체 라이브러리 복사 횟수로 회귀를 검사한다.

F01/F02 이후 UI **201개 파일·2,189개 테스트**, 관련 프로필 검사 161개, 직접 검사·i18n·typecheck·production 프런트엔드 build가 통과했다. 전체 lint는 오류 0개이며 기존 `CustomSelect` effect 의존성 경고 1개가 있다. jsdom의 canvas/pseudo-element 안내와 큰 workbook 청크 안내도 유지한다. 검사 기준·timeout·실패 제외는 변경하지 않았다.

Windows 개발 창에서 Strata의 런타임 → 프로필 → 옵션 화면을 열었다. native SSE 수정 후 다시 열린 개발 창에서는 llama.cpp의 성능 필드에 컨텍스트 `8192`를 입력하고, 변경 버리기를 거쳐 닫았다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시는 시작 전과 같았다. 저장·초기화·실제 추론은 실행하지 않았다.

## 2차 개선과 재검증

| 항목 | 변경과 보존 조건 | 근거 |
|---|---|---|
| N01 gateway SSE 파서 | 완성된 줄을 빌려 읽고 네트워크 청크마다 한 번만 소비한 앞부분을 정리한다. 기존 4 MiB 검사, CRLF·마지막 줄·청크별 UTF-8 처리, Responses/Anthropic의 서로 다른 DONE 처리, 취소와 모델 lease를 보존한다. | gateway 76개 검사와 dense-line·DONE 이후 잔여 데이터·과대 줄 회귀 검사. 커밋 `5ee6472`. SSE 단계의 전체 Rust 라이브러리 검사도 **1,141개 통과, 기존 ignored 6개**다. 실제 OS 자격 증명·개인 모델·ROCm 환경을 요구하는 opt-in 검사와 하위 프로세스 fixture를 성공으로 포함하지 않았다. |
| P01 게시 스냅샷 직렬화 | 검증에 사용한 JSON 문자열을 그대로 반환해 전체 직렬화를 2회에서 1회로 줄였다. 공개 함수·레거시 입력·스키마·오류 순서·행/설명/UTF-8 제한을 유지한다. | packed offline 설치·Node/browser import·스키마·독립 TypeScript 소비 검사. 1/1,000/10,000행의 요청 바이트와 SHA-256이 전후 동일하다. 10,000행 중앙값은 24.45→19.72 ms. 새 검사 코드의 템플릿 이스케이프 오류 4건도 전체 lint에서 찾아 고치고 패키지 검사를 다시 통과했다. 커밋 `36a1d21`. |
| F03 문서 검색과 컨텍스트 | 같은 문자 그대로의 비중첩 빈도를 정규식·일치 배열 없이 센다. 기존 첨부 순서와 컨텍스트 문구를 보존하며, 컨텍스트가 찬 뒤의 문서는 읽거나 순위를 계산하지 않는다. | Unicode·대소문자·중복 검색어·동점 순서·첨부 무변경·제외 문서 판독 0회 검사. 합성 점수/순서 및 실제 생성 컨텍스트의 전후 해시가 같다. 커밋 `2b17899`. |

F03의 32개 검색어·문서 4개 합성 비교에서, 각 64 KiB 문서의 전체 순위 계산은 7.37→5.87 ms, 각 1 MiB 문서는 113.51→90.97 ms였다. 이어서 컨텍스트에 들어가지 않는 나머지 첨부 계산을 없앤 효과를 별도로 측정했다. 같은 컨텍스트를 만드는 비용은 각각 5.71→1.47 ms, 90.72→22.64 ms였다. 단계별 기준을 섞어 비율을 계산하지 않으며, 문서 선택·순서·전달 내용을 바꾸지 않았다.

2차 UI 전체 검사도 **201개 파일·2,189개 테스트**를 통과했다. 새 RAG 사례는 직접 검사에 포함되며 직접 검사 전체·i18n·typecheck·build·lint도 통과했다. native의 후속 Responses 메모리 변경은 이 검사 결과의 범위에 포함되지 않는다.

추가 독립 교차 검토에서 프로필 메모·옵션 별칭·문서 검색의 관련 검사를 통과했다. 문서 검색은 시작 소스와 수정 소스를 동일 입력으로 비교한 순위 100건·컨텍스트 800건에서도 결과가 같았다. Unicode와 첨부 이름, 0·음수·비유한 예산을 포함해 기존 동작의 보존을 확인했다.

## Responses 이력 공유

N02는 각 응답에 전체 누적 메시지를 복사해 보관하던 구조를 부모 이력과 이번 요청의 메시지를 공유하는 구조로 바꿨다. 새 요청을 보낼 때만 전체 메시지 배열을 만들고, 잠금 안에서는 이력의 공유 참조만 가져온다. 공개 응답 JSON과 128개 응답 조회 한도, 기존 임의 퇴출 정책은 유지한다. 상위 응답을 삭제·취소하거나 퇴출해도 남아 있는 하위 응답은 기존 전체 대화를 이어갈 수 있다. 구현 커밋은 `ac36b85`다.

실제 loopback 검사에서 stream/non-stream 연속 요청의 전달 메시지, 상위 응답 삭제·취소, 다른 세션과 개인 upstream 인증, 퇴출 후 하위 응답의 계속 사용을 확인했다. 깊이 8,192 이력의 해제와 공유된 깊이 512 이력을 여러 소유자가 동시에 해제하는 합성 검사도 통과했다. 이는 운영 환경의 충돌을 재현했다는 뜻이 아니다.

합성 payload 비용 모델에서 64 KiB 메시지를 사용하는 깊이 128 이력의 보관량은 1,082,634,048→16,785,024바이트였다. 별도 계수 allocator로 측정한 합성 `String`/`Vec`/`Arc` 이력은 작은 메시지 깊이 128에서 1,576,032→25,600바이트, 큰 메시지 깊이 16에서 17,837,792→2,098,816바이트였다. 공개 응답·HTTP·`serde_json::Value`의 실제 비용이나 OS RSS를 측정한 수치로 확대하지 않는다.

최종 N02 소스에서 gateway **83개**, 독립 전체 Rust 라이브러리 **1,148개** 검사가 통과했고 기존 opt-in/fixture ignored 6개는 남아 있다. pinned Rust의 전체 target·feature Clippy도 경고를 오류로 처리해 통과했다. 전체 `cargo test` 시도는 병렬 빌드 중 Windows 페이징 파일 부족과 실행 중인 개발 GUI의 실행 파일 잠금으로 실패했다. 빌드 작업을 1개로 제한한 라이브러리 재검사는 통과했으며, 전체 실행을 통과했다고 기록하지 않는다. 시스템 페이징 설정·의존성·검사 제외 조건은 변경하지 않았다.

## 진행 중인 native·계약 검토

OpenCode의 1차 읽기 전용 감사에서 다음 후보를 찾았다. 아직 측정·구현·관련 검사·교차 검토가 끝나지 않은 항목은 성능 개선 성공으로 취급하지 않는다.

- 모델 카탈로그의 중복 탐색: 합성 100/1,000/10,000개 경로에서 호출 내 인덱스를 사용한 결과와 순서가 같았다. 10,000개 조건의 지역 변환은 159.25→2.36 ms였다. 아직 제품 구현에 반영하지 않은 설계 측정이다.
- GGUF 헤더·텐서 중복 파싱: 호출 경로의 반복 파싱을 확인했다. 검증·오류 순서와 facts-only 경로의 메모리 특성을 보존하는 설계까지 검토했으며 실제 구현과 계측은 남아 있다.
- 스냅샷 fingerprint의 반복 파일 I/O: 변조 전후 검출을 약화하는 캐시는 허용하지 않는다.
- 벤치마크 이력의 디렉터리 탐색 규모, 나머지 기능·도구 및 OS별 분기는 추가 상세 검토 대상이다.

이미 존재하는 경계·인증·프로세스 소유권·취소·변조 검출·데이터 이전을 비용이라는 이유로 제거하지 않는다. 채팅은 현재 idle 단계에서 이력을 저장하므로, 매 스트리밍 토큰마다 저장한다는 가정은 실제 호출 경로와 맞지 않았다. 실제 Linux/macOS 실행은 이번 Windows 검사의 성공으로 표시하지 않는다.

원본 감사·합성 측정·실패 재현·진행 상태는 `tmp/efficiency-review/`에 보관하고 커밋하지 않는다. Claude 감사는 실제 주간 사용량 제한으로 실패해 프런트엔드 수정은 직접 수행했으며, OpenCode의 감사 성공과 구분해 기록한다.

# 프로젝트 효율 검토 기록

전체 코드의 반복 검토와 개선을 진행 중이다. 아래 결과는 완료한 항목의 근거이며, 프로젝트 전체의 검토나 최적화가 끝났다는 판정이 아니다. 시작 소스는 `08c0916`이다.

이는 합성 변환 함수의 측정이며 GUI 전체 지연 시간이나 실제 엔진 추론 속도를 뜻하지 않는다. 실행 환경과 다른 작업의 부하에 따라 절대 시간은 달라진다. F01은 시간 임계치 대신 실제 전체 라이브러리 복사 횟수로 회귀를 검사한다.

F01/F02 이후 UI **201개 파일·2,189개 테스트**, 관련 프로필 검사 161개, 직접 검사·i18n·typecheck·production 프런트엔드 build가 통과했다. 전체 lint는 오류 0개이며 기존 `CustomSelect` effect 의존성 경고 1개가 있다. jsdom의 canvas/pseudo-element 안내와 큰 workbook 청크 안내도 유지한다. 검사 기준·timeout·실패 제외는 변경하지 않았다.

Windows 개발 창에서 Strata의 런타임 → 프로필 → 옵션 화면을 열었다. native SSE 수정 후 다시 열린 개발 창에서는 llama.cpp의 성능 필드에 컨텍스트 `8192`를 입력하고, 변경 버리기를 거쳐 닫았다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시는 시작 전과 같았다. 저장·초기화·실제 추론은 실행하지 않았다.

F03의 32개 검색어·문서 4개 합성 비교에서, 각 64 KiB 문서의 전체 순위 계산은 7.37→5.87 ms, 각 1 MiB 문서는 113.51→90.97 ms였다. 이어서 컨텍스트에 들어가지 않는 나머지 첨부 계산을 없앤 효과를 별도로 측정했다. 같은 컨텍스트를 만드는 비용은 각각 5.71→1.47 ms, 90.72→22.64 ms였다. 단계별 기준을 섞어 비율을 계산하지 않으며, 문서 선택·순서·전달 내용을 바꾸지 않았다.

추가 독립 교차 검토에서 프로필 메모·옵션 별칭·문서 검색의 관련 검사를 통과했다. 문서 검색은 시작 소스와 수정 소스를 동일 입력으로 비교한 순위 100건·컨텍스트 800건에서도 결과가 같았다. Unicode와 첨부 이름, 0·음수·비유한 예산을 포함해 기존 동작의 보존을 확인했다.

## Responses 이력 공유

N02는 각 응답에 전체 누적 메시지를 복사해 보관하던 구조를 부모 이력과 이번 요청의 메시지를 공유하는 구조로 바꿨다. 새 요청을 보낼 때만 전체 메시지 배열을 만들고, 잠금 안에서는 이력의 공유 참조만 가져온다. 공개 응답 JSON과 128개 응답 조회 한도, 기존 임의 퇴출 정책은 유지한다. 상위 응답을 삭제·취소하거나 퇴출해도 남아 있는 하위 응답은 기존 전체 대화를 이어갈 수 있다. 구현 커밋은 `ac36b85`다.

실제 loopback 검사에서 stream/non-stream 연속 요청의 전달 메시지, 상위 응답 삭제·취소, 다른 세션과 개인 upstream 인증, 퇴출 후 하위 응답의 계속 사용을 확인했다. 깊이 8,192 이력의 해제와 공유된 깊이 512 이력을 여러 소유자가 동시에 해제하는 합성 검사도 통과했다. 이는 운영 환경의 충돌을 재현했다는 뜻이 아니다.

합성 payload 비용 모델에서 64 KiB 메시지를 사용하는 깊이 128 이력의 보관량은 1,082,634,048→16,785,024바이트였다. 별도 계수 allocator로 측정한 합성 `String`/`Vec`/`Arc` 이력은 작은 메시지 깊이 128에서 1,576,032→25,600바이트, 큰 메시지 깊이 16에서 17,837,792→2,098,816바이트였다. 공개 응답·HTTP·`serde_json::Value`의 실제 비용이나 OS RSS를 측정한 수치로 확대하지 않는다.

최종 N02 소스에서 gateway **83개**, 독립 전체 Rust 라이브러리 **1,148개** 검사가 통과했고 기존 opt-in/fixture ignored 6개는 남아 있다. pinned Rust의 전체 target·feature Clippy도 경고를 오류로 처리해 통과했다. 전체 `cargo test` 시도는 병렬 빌드 중 Windows 페이징 파일 부족과 실행 중인 개발 GUI의 실행 파일 잠금으로 실패했다. 빌드 작업을 1개로 제한한 라이브러리 재검사는 통과했으며, 전체 실행을 통과했다고 기록하지 않는다. 시스템 페이징 설정·의존성·검사 제외 조건은 변경하지 않았다.

회귀 검사는 세 가지 비정상 값을 최상위와 파일 항목에 각각 넣은 6개 사례의 실제 수정 전 실패를 기록한 뒤 수정 후 통과했다. 유효한 추가 정보 3개와 다른 저장소·revision 필터도 전체 반환값으로 비교한다. 비교 과정에서 이전 테스트 바이너리가 재사용된 자료와 Windows 경로 표기가 달라 생긴 실패는 제외했다. 올바른 입력·같은 경로·별도 빌드 구분값·실행 파일 해시·실제 호출 계수로 결함 재현을 확인했으며, 비교를 통과시키기 위해 반환 필드를 제거하지 않았다.

최종 관련 검사 22개·Rust 라이브러리 1,159개·CLI 15개·fmt·전체 target/feature Clippy가 통과했고 기존 ignored 6개·1개는 유지한다. 현재 Cargo 산출물에 원본 `runtime_adapter_setup`·`runtime_adapters` 소스를 직접 컴파일한 통합 검사 2개도 통과했다. 이 직접 실행은 전체 Cargo 통합 검사 성공과 구분한다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시도 같다. 합성 Windows 검사이며 새로운 실제 모델 추론·GUI·다른 OS 검증이나 성능 개선을 입증한 결과로 확대하지 않는다.

## Python 내보내기와 보조 도구 검토

T01은 pinned `mlx-lm` wheel을 만들 때 이미 읽은 파일을 `RECORD`용으로 다시 해시하고, 파일마다 전체 크기를 다시 합산하던 작업을 줄였다. 같은 immutable 바이트의 raw digest 하나로 source record와 `RECORD`를 만들며, 중복 canonical 파일명은 기존 값을 뺀 크기와 마지막 내용을 사용한다. 변경된 파일을 탐지하는 앞선 source-record 재검증은 유지한다. 구현 커밋은 `3e2d23c`다.

합성 101개 파일의 실제 원본·수정 script 비교에서 direct URL 경로의 SHA-256 호출은 203→102회, source-record fallback은 304→203회였다. 누적 합산은 102회·5,252개 항목 재순회에서 증분 계산으로 바뀌었다. 읽기 횟수와 wheel member 내용·순서, source JSON·RECORD 해시는 같았다. 이는 실제 엔진의 내보내기 시간·RSS 측정이 아니다. portable 검사 8개를 포함한 provider 검사 20개와 별도 provider 검사 5개, runtime-adapter 12개·model-repair 5개가 통과했다. 64MiB·256MiB 경계는 작은 파일에 통제된 크기를 적용했고, 10,000개 항목은 같은 빈 파일을 서로 다른 이름으로 매핑했다. 이 경계 검사를 대용량 실제 I/O 검사로 표시하지 않는다. 기존 실제 ZIP·offline pip 임시 설치·재캡처·변조 거부 검사는 유지했다.

T02는 runtime의 버전·도움말 출력을 전부 보관한 다음 잘라내던 수집기를 바꿨다. stdout·stderr 각각 최대 65,536자를 보관하면서 끝까지 읽고 디코딩한다. stdout 우선 반환·활성 locale·개행 변환·원래 비정상 종료 오류 우선순위와 15초 제한을 유지한다. 한도 뒤의 잘못된 인코딩도 거부하며, 하위 프로세스가 pipe를 계속 잡고 있어도 수집 제한을 지킨다. Windows native 오류는 원래 Win32 코드와 설명으로 전달한다. 구현 커밋은 `58bc9b5`다.

같은 합성 child가 각 stream에 8MiB씩 출력하는 원본·수정 helper를 별도 프로세스에서 각 3회 비교했다. 여섯 번 모두 반환 65,536자의 해시가 같았고, 최종 수집기도 전체 16MiB를 읽었다. Python 할당 최고치 중앙값은 33,630,277→289,186바이트, 1ms 간격으로 관측한 working-set 증가량 중앙값은 16,969,728→479,232바이트였다. 측정 프로세스에는 관측 thread 비용이 포함되며, 샘플은 실제 최고치를 보장하지 않는다. 수집 시간 중앙값은 0.250→0.422초로 늘었다. 이 결과를 GUI·실제 엔진·모델·GPU 메모리나 전체 속도의 개선으로 해석하지 않는다.

최종 Python runtime-adapter 검사 21개가 통과했다. 대량 출력·Unicode 문자 제한·개행·한도 뒤 디코딩 오류·비정상 종료·시간 제한과 direct child 정리를 포함한다. 최종 native `--lib --bins --examples`도 라이브러리 1,158개·CLI 15개와 다른 binary·예제 test target 빌드를 통과했고 기존 ignored 6개·1개는 유지한다. integration을 포함한 Cargo 실행은 실행 중인 개발 GUI의 파일 잠금으로 실패했다. GUI를 종료하지 않고, Cargo로 최신 라이브러리와 fixture만 빌드한 뒤 원본 `runtime_adapter_setup`·`runtime_adapters` 테스트 소스를 해당 산출물에 직접 컴파일해 실행한 두 검사는 통과했다. 이 직접 실행을 전체 `cargo test` 성공으로 기록하지 않는다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시도 같다. Linux/macOS의 실제 출력 수집 검사는 수행하지 않았다.

T03은 Strata 준비와 모델 미선택 probe에서 같은 설정의 JSON 해석·정책 검증을 2회에서 1회로 줄였다(`b8c9e4e`). 두 번째 원문 읽기와 실행 파일·tokenizer 존재 확인은 유지한다. 다른 모델 설정을 지정한 probe는 계속 두 설정을 각각 검증하고 native build를 비교한다. 사용하지 않게 된 내부 JSON 래퍼와 setup의 설정 지역 변수도 제거했다. CLI·manifest·draft·모델·옵션·argv·artifact 순서는 유지하며, 출력 수집 코드는 바꾸지 않았다.

실제 준비·probe 함수의 합성 비교에서 정상 출력·오류 10개 사례가 같았다. 약 360바이트 설정과 인자 1,000개를 넣은 약 19KiB 설정 모두 읽기·파일 확인·하위 명령 실행 횟수는 같고 JSON 해석만 줄었다. 준비 도중 설정 파일을 교체하면 예전 구현은 서로 다른 시점의 정보를 섞어 반환할 수 있었다. 수정 후에는 원문 차이를 감지해 거부한다. 최초 검증 후 실행 파일이나 tokenizer가 사라지는 경우도 실제 임시 파일로 재현해 후속 동작 전에 실패하는지 확인했다.

최종 Python runtime-adapter 검사 27개와 구문 검사가 통과했다. 독립 검증은 보관된 정규화 JSON의 해시와 전체 결과를 다시 계산하고, 다른 모델의 별도 검증 및 출력 수집 코드의 바이트 보존도 확인했다. Git revision만 고정한 fixture를 사용했으며, 도움말용 합성 모듈과 Python 버전 명령은 실제 subprocess로 실행했다. 실제 Strata 추론·사용자 모델·다른 OS 실행이나 지연 시간·RSS 개선을 입증한 결과는 아니다.

Python helper와 플랫폼 보조 스크립트는 실제 embedded 호출·CI·운영자 도구로 연결돼 있어 미사용으로 삭제하지 않았다. 검증 시점이 다른 읽기는 임의로 합치지 않는다.

T04는 compatibility wheel을 읽을 때 각 파일의 ZIP metadata를 얕게 복사하던 코드를 제거했다(`a37c415`). 출력은 별도의 새 metadata를 구성하므로 입력 descriptor를 다시 복사할 필요가 없었다. 실제 전체 `build_wheel` 함수의 합성 101개 파일 비교에서 복사는 101회→0회였으며, 출력 ZIP 바이트·audit·파일 순서·내용·속성·라이선스·RECORD는 같았다. 관련 Python 15개 검사도 통과했다. source 준비의 재해시는 출처·변조 검증에 필요해 유지했고, 실제 upstream wheel·설치·다른 OS 실행이나 시간 개선을 입증한 결과는 아니다.

같은 변경의 후속 해시 캐시 후보는 채택하지 않았다. 101·1,000개 파일과 세 가지 패치 크기의 전체 wheel 생성 호출을 순서를 교대해 각각 12회 측정했다. 여섯 조합 중 네 조합의 중앙값은 늘었고, 두 조합의 감소는 1% 미만이며 측정 범위가 겹쳤다. 모든 파일에 추가되는 조회와 코드 복잡성을 정당화할 이점이 확인되지 않아, 검증된 ZIP 복사 제거만 유지했다. 반환 결과가 같거나 해시 호출 한 번이 줄었다는 사실만으로 더 효율적이라고 판정하지 않았다.

빌드·패키징 helper 다섯 개도 package script·workflow·플랫폼 분기·운영 문서까지 추적했다. 이 파일들에서 삭제할 미사용 내부 코드는 확인하지 못했다. 대신 Linux release의 사전 검사와 `package:tauri`가 CLI release 빌드를 두 번 호출하는 것을 확인해, 중간 검사에서 사용하지 않는 앞선 호출 한 줄을 제거했다(`24efa45`). CLI 빌드 → frontend 빌드 → GUI packaging 순서와 path remap·fixture 제외·모든 검사·다른 OS의 명령은 유지한다. 기존 YAML parser를 통한 workflow 판독·명령 보존 확인과 Node packaging 검사 3개가 통과했다. 실제 Linux CI·패키지 생성·설치는 실행하지 않았으며 빌드 시간 개선을 측정한 결과도 아니다.

## 플랫폼 검증 도구의 중복 작업

T05는 읽기 전용 DMG의 같은 앱 서명 정보를 인접한 두 assertion에서 각각 조회하던 호출을 한 번으로 줄였다(`40551e1`). 엄격한 서명 검증과 GUI·CLI 바이너리의 개별 조회는 유지한다. 전체 파일이 이 변경만 포함하는지 확인하고 실제 변경 소스 블록의 정상·오류 8개 사례를 비교했다. 해당 블록의 조회는 4회에서 3회로 줄었으며 Node 구문·린트 검사가 통과했다. 실제 macOS의 DMG·codesign·Swift·GUI 검사는 실행하지 않았고 시간·RSS 개선을 측정한 결과도 아니다.

T06은 Windows PR runtime 패키징에서 같은 디렉터리 이름을 DLL마다 다시 계산하던 작업을 디렉터리마다 한 번으로 줄였다. 명시된 브랜치 이름이 있으면 사용하지 않는 Git fallback 조회도 생략한다(`f6c7611`). 비어 있거나 공백인 이름의 fallback·오류 처리, CRT 탐색·System32 필터·복사 순서·파일 해시·출처·manifest 정렬은 유지한다. 실제 workflow의 repository는 PR head 저장소이고 URL은 기준 upstream의 PR을 가리키므로 이 계약도 보존한다.

전체 PowerShell 소스를 합성 Unicode·공백 경로와 복수 CRT 디렉터리에서 실행한 12개 변형은 정상 패키지 8개와 의도한 오류 4개를 확인했다. 추출한 ZIP 항목의 순서·이름·크기·내용 해시, 출처·manifest 본문, 복사된 바이트·속성과 오류가 같다. 관련 경로 계산은 17회→4회, 명시된 브랜치의 Git 조회는 1회→0회다. ZIP 생성 시각에 따른 전체 archive 바이트 차이와 실제 MSVC 환경·CI·발행·추론은 이 결과에 포함하지 않는다.

Linux 런처 등록의 재판독을 합치는 후보는 철회했다. 첫 관찰 이후 새 AppImage 런처가 생성되거나 기존 항목을 교체하면 후보가 이를 개발용 항목으로 덮어쓰는 두 사례가 실제로 재현됐다. 운영 코드를 원래 바이트로 복원하고 임시 파일시스템에서 전체 등록 함수를 호출하는 회귀 검사 두 개를 추가했다(`cec0a8a`). 후보에서는 두 검사가 실패했고 복원 후 8개 통과·기존 GIO 검사 1개 skip이다. 이것은 일반적인 원자적 등록이나 실제 Linux 데스크톱 검증을 입증하지 않는다.

runtime smoke·플랫폼 검증·설치 도구 15개는 실제 호출과 데이터 흐름을 추가 검토했다. readiness·취소·프로세스 정리·설치 전후 관찰은 각각 필요해 제거하지 않았다. provider runtime의 Node 검사 40개와 합성 self-test도 통과했다. 실제 엔진·설치·Linux/macOS 실행은 이 합성·정적 검사의 성공과 구분하며, [플랫폼 검증 안내](cross-platform-validation.md)와 각 OS 인계의 기존 명령을 유지한다.

## 공통 API·설정 참조 감사

native 공유 응답의 오류 생성에서 양쪽 값이 같은 조건식과 같은 서비스 코드를 다시 대입하는 분기를 제거했다(`b2e91e9`). HTTP 오류 종류·메시지·재시도 여부·상태·Retry-After·서비스 코드, 정상 응답과 receipt 검증은 그대로다. API 관련 8개 파일·48개 검사, 발행 화면 연계 2개 파일·21개 검사와 별도 공유 전송·제어기 3개 파일·19개 검사가 통과했다. 겹치는 검사는 합산하지 않는다.

## 공통 화면과 실행 옵션의 반복 작업

세션 polling 훅에서 렌더마다 만들던 콜백 보관 객체를 두 개의 지속적인 ref로 바꿨다(`a077d5c`). 최신 콜백 전달과 기존 구독의 수명은 유지한다. 반면 Flash 메시지의 내부 함수에 memo hook을 추가하는 후보는 실제로 함수 표현식 생성을 줄이지 못해 철회했다.

선택 메뉴는 바뀌지 않은 라벨에 이벤트를 매번 다시 연결하는 작업과 강조 항목 이동 때의 불필요한 크기 측정을 줄였다(`34cc008`). 선택지나 글꼴 때문에 실제 크기가 바뀌면 다시 배치하고, `ResizeObserver`가 없는 환경에는 렌더마다 확인하는 기존 호환 경로를 유지한다. 상태 갱신에는 최종 화면 경계 보정값을 비교하며, DOM 측정은 갱신 함수 밖에서 수행한다. 전체 옵션을 매 렌더 문자열로 만드는 후보와 갱신용 ref 카운터는 제외했다. 옵션 직접 입력의 검색어 소문자 변환도 옵션마다 반복하지 않는다.

## Windows 프로세스 종료 확인

Windows의 job 통계가 0이 된 뒤에도 독립적으로 보관한 하위 프로세스 핸들이 아직 종료 신호를 보내지 않은 실패를 재현했다. job 핸들을 직접 기다리는 후보도 반복 검사에서는 통과했지만, [Microsoft의 job 신호 설명](https://devblogs.microsoft.com/oldnewthing/20130405-00/?p=4743)은 시간 제한 종료의 신호를 설명하므로 일반적인 명시적 종료 완료 계약으로 채택하지 않았다. 최종 수정은 실제 job 멤버의 프로세스 핸들을 보관하고 종료 신호를 확인한다(`d0d04e1`).

멤버 목록은 크기 부족과 부분 반환을 처리하는 제한된 조회로 수집한다. 시작 직후와 종료 요청 전에 핸들을 보관해 PID 재사용을 구분하고, 조회·핸들 확보가 불확실하면 정리 완료를 보고하지 않는다. 기다린 뒤 목록과 모든 보관 핸들의 신호를 하나의 짧은 잠금에서 재확인한다. 막히는 대기 동안은 잠금을 잡지 않는다. Win32 오류는 [공식 오류 조회 계약](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-getlasterror)에 따라 시계를 다시 읽기 전에 보존한다. 중복 멤버 확인 helper와 별도의 0초 관찰 인자는 제거했다.

실행 중인 트리의 0초 확인은 거부하고 이미 종료를 관찰한 트리는 즉시 확인할 수 있도록 검사했다. 부모가 먼저 종료한 뒤 남은 하위 프로세스, 실제 복수 멤버 조회, 취소·등록 해제·소유권을 넘긴 프로세스도 관련 검사에 포함한다. 원래 실패 검사의 대기·경과 시간 조건은 유지하며, 잘못된 Unix 조건부 경계는 커밋 전에 복구했다. 최종 집중 검사 13개와 전체 Rust 라이브러리 **1,162개**, CLI **15개**, 전체 fmt와 모든 target·feature의 Clippy가 통과했다. 라이브러리 6개·CLI 1개의 기존 opt-in 및 하위 프로세스 fixture 표시는 유지하고 새로운 skip은 추가하지 않았다.

범위는 Windows에서 실행한 합성 프로세스 및 자동 검사다. Linux 교차 검사는 외부 libdbus·Wayland의 pkg-config 설정에서 중단되어 앱의 Linux 빌드 성공으로 기록하지 않는다. Unix 알고리즘·공개 API·기본 설정·의존성·lockfile은 보존하며 Linux/Mac 기기에서의 빌드·소유 프로세스 종료·취소·headless 유지 동작 확인은 후속 작업이다. 전체 설정·프로필 7개·대화 8개 파일 해시는 최종 검사 뒤에도 같다. 이번 검사로 소스 폴더에 새로 생긴 Python bytecode는 없었으며, 원래 임시 자료와 사용자 데이터를 정리 대상으로 삭제하지 않았다.

## 모델 설정과 런타임 옵션의 반복 계산

모델 설정 52개 경로와 런타임 화면 54개 경로의 실제 호출·상태 흐름을 추가 검토했다. 검토한 원본과 수정본의 전체 파일 해시를 별도로 대조했으며, 이 수는 해당 경로의 검토 근거이지 모든 함수의 최적화나 프로젝트 전체 완료를 뜻하지 않는다.

설정 붙여넣기는 `-1`, `-0.5`, `-1e3`을 다음 옵션으로 오인하지 않고 값으로 읽는다(`e3e6cf7`). 허용 범위를 벗어난 값은 계속 거부하며, `--`·단독 `-`·문장부호와 Unicode가 있는 미확인 옵션은 기존 옵션 경계를 유지한다. 프로필의 저장된 인자 요약도 같은 음수 예외를 사용해 미확인 옵션들을 앞선 값에 합쳐 표시하지 않는다(`7cd1086`). 실제 import 및 컴포넌트 검사에서 수정 전 실패와 수정 후 성공을 확인했다.

런타임 카탈로그의 provider별 배열 누적과 환경 목록의 반복 필터, 제거 확인의 이름 중복 검색, 장치 적합도 반복 조회를 줄였다(`46fae8b`). 원래 provider·runtime 순서, 종류가 다른 같은 이름, 첫 번째 장치 판정, 미확인 장치의 fallback과 안정적인 정렬은 유지한다. 환경 화면의 목록은 native API에서 받아 자체 상태로 보관하므로 이 배열의 변경 경계를 기준으로 그룹화한다. 앞선 공유 설치 목록의 실제 갱신 함수와는 소유권이 다르며, 두 경로의 관찰 경계를 합치지 않는다.

옵션 편집기는 스키마의 키를 한 번 색인하고 반복 항목의 별칭 배열을 추가할 때 전체 배열을 다시 복사하지 않는다. 실제 Chrome 비교 중에는 기존 별칭 표시 문제도 재현했다. `-P`와 `--pair`가 섞인 반복 항목에서 값 하나를 편집하면, 저장된 순서와 인자는 보존되지만 두 번째 선택기가 `-P`로 잘못 표시됐다. 기본 별칭을 뜻하는 `null`과 행 정보가 없는 경우를 구분해 고쳤다(`535ee2b`). 실제 컴포넌트 회귀 검사는 두 선택기·값·다른 옵션 사이의 순서를 함께 확인하며, 옵션 편집기와 순서 검사 30개가 통과했다.

최종 프런트엔드는 타입 검사·전체 린트·production 빌드와 UI **203개 파일·2,225개 검사**, 4개 언어의 직접 번역 검사를 통과했다. 기존 jsdom의 canvas·pseudo-element 안내와 workbook 청크 안내는 유지한다. 이 프런트엔드 검사는 아래 네이티브 도움말 처리의 최종 검사와 별도로 수행했다.

## 도움말 처리의 중간 복사와 사용하지 않는 계산

도움말의 옵션 구문을 식별할 때 만든 파싱 결과를 실제 그룹·줄 위치와 함께 재사용한다(`4961d98`). 공백 구간과 모든 줄을 모으던 임시 목록, 전체 도움말 문자열의 복사, 사용하지 않는 choices 계산과 중복 arity 계산도 줄였다. 출처 문자열과 줄 위치, 불확실한 정보의 처리·오류 순서·입력 한도는 유지한다.

음수 전용 옵션의 충돌 조회는 필요한 입력에서만 색인을 만들고, 추가 출처 정보가 없는 옵션 병합은 문서 색인을 만들지 않는다. 문서 ID는 빌려 사용해 새 문자열을 복사하지 않는다. 이전 스냅샷이 없는 설명 생성은 자기 자신과 전체 옵션을 비교하던 작업을 없애고 미확인 저장 키만 정렬·중복 제거한다. 저장 키도 없으면 이 조회 색인을 생략한다.

실제 원본·최종 crate의 공개 함수 `parse_help_report`, `apply_overlay`, `describe`를 동일한 합성 입력으로 호출했다. 작은 도움말과 1,000개 옵션, 별칭·음수·Unicode·stderr·절단·디코딩 오류, 정상·외부 출처, 빈 저장 키·이전 스냅샷·바인딩 오류를 포함한 24개 결과의 전체 직렬화 길이와 해시가 같다. 최종 소스·harness·고정 바이너리의 해시를 독립 확인하고 최종 바이너리의 결과를 다시 비교했다.

실제 등록→도움말 확인→저장된 실행 인자 전달, 명시적 인코딩, 반복 옵션 순서, 모순된 사실의 거부를 검사하는 기존 통합 테스트 네 개가 통과했다. 합성 엔진을 사용한 호출 경로 검사이며 개인 엔진의 실제 추론으로 계산하지 않는다. 최종 Rust `1.98.0`의 라이브러리 **1,162개**, CLI **15개**, 전체 fmt와 모든 target·feature의 Clippy도 통과했다. 집중 도움말 검사 66개는 전체 라이브러리 검사와 겹치므로 합산하지 않는다. 기존 ignored는 라이브러리 6개·CLI 1개로 유지한다.

debug 프로필의 전체 함수 합성 측정은 입력별 편차와 일부 증가도 보여, 릴리즈·GUI·추론 속도 개선 수치로 확대하지 않는다. 이 변경은 불필요한 복사·반복 파싱·조건 없는 색인 구성을 줄인 결과다. 실제 도움말 수집의 전후 identity·해시 재확인 코드는 변경하지 않았으며 공개 API·저장 데이터·의존성·lockfile도 유지한다. 최종 검사 뒤 설정 전체·프로필 7개·대화 8개 해시는 같았고 소스 폴더에 새 Python bytecode는 없었다.

배포 자산·설정·CI·법적 고지 37개도 실제 동적 참조와 빌드·배포 목적을 정적으로 대조했다. 모델 아이콘·폰트·플랫폼별 패키지 아이콘·고지와 재현 가능한 빌드 설정은 유지했다. `favicon.ico`와 `icons/icon.png`는 안전하게 제거할 근거를 확정하지 못해 보존했다. 이 감사로 워크플로 실행이나 설치 패키지 검증을 수행했다고 표시하지 않는다.

## 벤치마크 출처와 소유권 기록의 중복 처리

벤치마크·공유·저장소의 18개 경로를 실제 호출과 검증 경계에 따라 추가 검토했다. 모델 출처 수집은 이미 확인한 다운로드 영수증의 repository 값을 재사용하고, 소유권 기록은 origin URL을 한 번 검증·파싱해 destination 검사에 전달한다(`8bc1c5c`). 성공한 업로드 상태 조회 뒤의 불필요한 명시적 값 폐기도 제거했다. 오류 응답의 Retry-After와 상태·코드·본문 비공개 처리, 소유권·해시·시각·잠금 검사는 보존한다.

서버의 사람이 읽는 오류 메시지를 결과에 쓰지 않더라도 `Option<String>` 필드는 문자열·null·누락과 잘못된 자료형을 구분하는 입력 검증을 수행한다. 이 필드와 기존 역직렬화 경계는 유지했다. 원본과 최종 18개 파일의 전체 바이트를 대조했으며, transport의 변경은 불필요한 폐기문 하나로 제한됐음을 별도로 확인했다.

관련 벤치마크 검사 **123개**와 최종 전체 Rust 라이브러리 **1,162개**, CLI **15개**, 전체 fmt·모든 target과 feature의 Clippy가 통과했다. 기존 라이브러리 6개·CLI 1개의 opt-in 및 프로세스 fixture 표시는 유지했다. 최종 검사 뒤 설정 전체·프로필 7개·대화 8개의 해시는 같았다. 실제 엔진·발행 서비스·OS 자격 증명·GUI를 새로 검증한 결과로 확대하지 않는다.

완료된 기준 빌드의 작업용 Cargo 캐시 **4,716개 파일·8,641,653,089바이트**도 정리했다. 소스 보관본·harness·원시 로그·고정 바이너리는 보존했고, 별도 진행 중인 빌드 캐시는 유지했다. 정리 전후에 원본과 최종 고정 바이너리를 각각 실행해 기존 24개 전체 결과와 일치하는지 확인했다.

## 채팅·탐색의 반복 계산과 설정 입력 상태

채팅의 임베딩 세션 선택기는 같은 렌더에서 만든 필터 결과를 표시·목록·이전 선택 확인에 재사용한다(`2baff0cb`). UI의 최대 세 번 조회를 한 번으로 줄였으며, 실제 대상 선택 함수의 별도 필터는 유지한다. 전체 경로의 최대 조회는 네 번에서 두 번으로 줄었다. 벤치마크 설명의 상태를 캡처하지 않는 Markdown 링크 렌더러와 앱의 고정 탐색 목록도 재사용한다(`74d1130f`, `a3932ab5`). 링크·HTML 차단, 동적 언어·테마·상태와 탐색 순서는 보존한다. 문서 설명도 엔진 중립적인 로컬 작업 공간과 런타임 어댑터 역할에 맞췄다(`f437d635`).

조건이 붙은 자동 기본값의 안내 누락도 수정했다(`fef389b8`). 합성 도움말에서 `--load-mode: auto`로 계산된 기본값을 실제 컴포넌트에 전달해 수정 전 실패와 수정 후 안내 표시를 확인했다. 기본값 파싱·출처·검증 범위는 그대로다.

설정 화면의 실제 입력 흐름에서는 다음 세 문제를 재현하고 고쳤다.

- 샘플러를 드래그하는 동안 부모가 목록을 교체·축소하면 이전 인덱스에서 `undefined`가 전달돼 React 이벤트 예외가 발생했다. 내용이 바뀐 목록의 드래그를 무효화하고 인덱스·항목을 확인한다(`504582e2`). 기존 순서·중복 제거·최대 개수·콜백·키보드 이동은 유지한다.
- 개별 필드를 초기화해도 직접 입력 모드와 일부 오류 상태가 남았다. 해당 필드의 모드·초안·오류만 정리하고 다른 필드의 작성 중인 값과 기존 설정은 보존한다(`09215864`). 실제 편집기 검사에서 잘못 입력한 Min-p 초안과 저장 값 `0.2`를 유지하면서 Mirostat만 초기화하는지 확인했다.
- 현재 목록에 없는 저장 값이 첫 번째 고정 선택값이나 `auto`로 표시됐다. 해당 문자열을 현재 선택 항목으로 표시하고 명시적인 선택에만 새 값을 반영한다(`e7b5bbc2`). 공통 정규화·스키마 검증·엔진 지원 판정은 바꾸지 않는다.

전체 UI 검사에서 시간 초과가 난 70개 옵션 표시는 같은 DOM의 반복 검색을 한 번으로 줄이고, 70개 전체와 양끝 접근성 이름을 확인하도록 정리했다(`25713b0c`). 관리 인자·프리뷰·점검 종료 검사는 유지했고 제한 시간·옵션 수·실행기 설정은 바꾸지 않았다. 계측은 jsdom 검사 비용을 확인한 근거다.

최종 수정 뒤 타입 검사·전체 린트·production 빌드·UI **205개 파일·2,232개 검사**와 4개 언어의 직접 번역 검사가 통과했다. 검사 전후 14개 파일의 전체 해시는 같았고 설정 전체·프로필 7개·대화 8개도 보존됐다. 처음 발생한 시간 초과와 각 결함의 실패 근거는 로컬 원시 자료에 남겼다.

실제 컴포넌트를 가져오는 채팅·설명 편집·튜닝 검증 페이지와 빌드 근거는 준비했다. 새 튜닝 페이지는 현재 구현을 사용하며 브라우저에서 원본과 수정본을 비교한 결과는 아직 없다. 현재 Chrome과 인앱 브라우저 연결이 없어 데스크톱·작은 창·키보드·초점·실제 드래그·console 재검증은 남아 있다. 나머지 소스 검토와 함께 이어서 수행한다.

## SDK의 중복 검증과 수치 집계

공개 benchmark-contracts SDK의 빌드·export·타입·검증·복구·집계·패키지 소비 검사 10개 경로를 추가 검토했다. 서비스 시각 검증은 JavaScript가 읽을 수 있다는 이유만으로 비 ISO 날짜 문자열을 허용하던 문제를 고쳤다(`4f24ca0`). 날짜·시각·offset의 범위와 Gregorian 달력을 확인하며 원문 문자열, 소수 초, offset, 소문자 표기와 4자리 연도 `0000`을 보존한다. 서비스의 `date-time` 계약은 [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339.html)의 형식을 기준으로 한다. 기존 JavaScript 검사에서 거부하던 윤초는 계속 거부하며 전체 RFC 입력을 새로 지원한다고 주장하지 않는다.

벤치마크 집계는 유한한 큰 입력에서도 평균·표준편차가 `Infinity`가 되지 않도록 합이나 제곱합이 넘칠 때만 크기를 나눠 계산한다(`cbfa142`). 보통 입력은 기존 계산 경로를 유지한다. 실제 표현 범위를 넘는 속도 비율은 사용할 수 없는 값인 `null`로 표시한다. 메모리 평균을 계산한 직후 최댓값으로 덮어쓰던 중복 순회도 없앴고, 큰 배열을 함수 인자로 펼칠 때 발생하던 `RangeError`를 제거했다. 이전 최댓값 계산의 음수 0·양수 0 구분도 보존한다.

실제 원본과 수정본의 전체 공개 함수를 합성 정상 입력 **167개 묶음**으로 대조했다. 전체 결과와 약 2MB의 직렬화 길이·해시·키 순서가 같았다. 두 `Number.MAX_VALUE` 입력의 평균은 같은 유한 값, 표준편차는 0이며, 원본에서 예외가 발생한 **15만 행** 입력도 표본 수와 메모리 최댓값을 유지했다. 이 검사는 실제 소스를 사용한 함수 결과 비교이며 앱·엔진의 지연 시간이나 RSS 측정이 아니다.

복구 코드에서는 파싱된 객체의 정확한 키 목록을 이미 확인한 뒤 반복하던 네 키의 존재 검사와 전용 helper만 제거했다(`7bb40d2`). 버전·정규 base64url·UUID·origin·비밀 길이·전체 입력 한도와 잘못된 자료형의 거부는 유지한다.

실제 공개 패키지를 pack·오프라인 설치한 소비자의 회귀 검사와 Node·브라우저형 ESM·스키마·개인정보 경계·타입 선언 검사가 통과했다. 최종 앱 타입 검사·전체 린트·production 빌드와 UI **205개 파일·2,232개 검사**도 통과했다. 검사 전후 SDK 10개 파일과 앞선 프런트엔드 14개 파일의 바이트가 같았고, 의존성·lockfile·toolchain·실행기 설정과 사용자 설정 전체·프로필 7개·대화 8개는 보존됐다.

설정·개발자·업데이트 화면의 별도 24개 파일도 실제 함수·호출·구독·초기화·삭제·키 비노출 경계를 대조했다. API를 다른 포트로 시작했다가 중지하면 포트가 되돌아간다는 의심은 실제 hook 검사로 반증했다. 이 범위에서 삭제나 수정의 근거를 확정하지 못한 코드와 검사는 유지했다. 이 정적 감사와 합성 hook 검사도 실제 GUI 재검증을 대신하지 않는다.

## 공유 작업의 측정 격리와 호출 소유권

공유 준비·복구에서 유휴 상태를 확인한 뒤 잠금을 놓아, 측정 시작과 실제 Vault·소유권 파일 작업이 겹칠 수 있던 경합을 수정했다(`ec0a8d4`). 기존 operation 잠금을 짧은 작업의 실제 blocking closure 안으로 이동해 작업이 끝날 때까지 보관한다. 부모 future가 취소돼도 진행 중인 작업이 잠금을 일찍 반납하지 않는다. 측정은 잠금을 기다리는 대신 즉시 거부하며, 정상 Ready 서버의 사용은 공유를 막지 않는다. 네트워크 응답이나 사용자의 파일 대화상자를 기다리는 동안에는 이 잠금을 보관하지 않는다.

공유 페이지 열기도 같은 소유권 경계를 사용한다. 실제 OS 호출을 대기열에 넣은 뒤 취소되면, closure 내부의 generation 검사에서 거부해 이전 인증·관리 페이지를 열지 않는다. OS 호출이 이미 시작된 뒤에는 강제로 중단할 수 없으므로 짧은 호출 구간만 보호한다. 릴리즈·모델 페이지의 동기 OS 호출도 async 실행 스레드 밖으로 옮겼다(`7e1091e`). URL 검증과 오류 비공개 처리는 유지했다. 도움말 인자를 직접 이동하고 공유 origin의 불필요한 복사도 제거했다(`ec44f7f`, `ec0a8d4`).

실제 준비·복구 함수를 MockVault·합성 임시 저장소로 호출해 두 실행 순서와 부모 취소를 확인했다. 브라우저 검사는 production helper와 주입한 opener로 Ready 사용·측정 거부·실제 대기열 등록 후 취소를 검증했다. 처음 검사 자체가 잠금을 반복 획득해 작업과 경합한 실패는 보존했다. 실제 future를 Pending까지 실행한 뒤 취소하도록 고쳤으며 제한 시간을 늘리거나 단독 검사 성공으로 전체 실패를 대신하지 않았다. 공유 명령 검사 **26개**와 최종 Rust 라이브러리 **1,170개**, CLI **15개**, 전체 fmt·모든 target/feature의 Clippy가 통과했다.

최종 검사 전후 네이티브 14개 파일의 바이트가 같았고, 설정 전체·프로필 7개·대화 8개도 보존됐다. 등록된 IPC·공개 응답·직렬화·설정·저장 데이터·잠금·취소·해시·readiness 계약은 유지한다. 기존 라이브러리 6개·CLI 1개의 opt-in 및 OS fixture 표시는 그대로다. 실제 OS Vault·브라우저·설치·추론을 실행한 결과나 전체 앱의 지연 시간·RSS 수치로 확대하지 않는다.

## 대화 저장의 크기와 실패 복구

네이티브 저장소가 읽기 제한을 넘는 이미지·대화도 저장 성공으로 반환하던 문제를 고쳤다(`c20ff40`). 합성 임시 저장소에서 기존 제한보다 큰 이미지는 저장 후 빈 이미지로 복원되고, 큰 대화는 다음 로드에서 제외되는 동작을 재현했다. 실제 사용자 대화나 설정은 검사의 입력으로 사용하지 않았다.

기존 이미지 64 MiB·대화 JSON 256 MiB 제한을 저장에도 적용한다. 유효한 base64의 디코딩 크기를 먼저 확인하고, 첨부를 별도 파일로 바꾼 뒤 최종 JSON을 한 번 직렬화하면서 한도를 검사한다. 원래 입력 JSON 전체 크기를 이미지 첨부의 허용 여부로 사용하지 않는다. 거부된 저장은 이전 대화와 첨부를 보존하며, 이번 시도에서 새로 만든 첨부만 정리한다. 이미지 순서·중복 내용·Unicode·미지 필드·잘못된 data URL의 기존 처리와 저장 형식은 유지한다.

경계·교체 실패·import 거부·첨부 복원 검사 12개와 최종 Rust 라이브러리 **1,175개**, CLI **15개**, fmt·모든 target/feature의 Clippy가 통과했다. 기존 라이브러리 6개·CLI 1개의 opt-in 및 OS fixture 표시는 유지했다. 검사 후 네이티브 10개 파일의 전체 바이트와 설정 전체·프로필 7개·대화 8개 보존도 확인했다. 이 근거는 대화 저장 수정 시점의 결과이며 이후 게이트웨이 수정이나 실제 GUI·엔진·후속 OS 검증을 포함하지 않는다.

## 게이트웨이의 입력 경계와 종료 정리

완성된 HTTP 헤더의 끝을 찾은 뒤에도 기존 64 KiB 제한을 적용한다(`76a1e47`). 정확히 한도인 헤더는 허용하고 1바이트 초과 및 나뉘어 도착한 초과 헤더는 거부한다. 작은 헤더와 큰 본문이 같은 read에 들어오는 정상 요청은 보존한다. 게이트웨이 상태 잠금이 poisoned 상태여도 소유한 listener를 꺼내 잠금 밖에서 종료하도록 고쳤으며, 강제 종료 경로에도 같은 처리를 적용했다(`5644b16`). 실제 loopback 연결 종료와 포트 반환을 검사했다.

모델 목록은 기존 모델명·세션 순서 정렬 뒤 인접 항목만 비교해 같은 모델의 세션별 이름을 붙인다(`956af1c`). 항목마다 전체 목록을 다시 세던 중복 작업을 없애면서 기본 세션·명시적 세션 선택·모호한 모델명 거부는 유지한다. multipart의 중복 스캔 의심은 실제 검색이 첫 일치 지점에서 멈추고 다음 시작점을 앞으로 옮긴다는 사실과 맞지 않아 철회했으며, 해당 코드는 바꾸지 않았다.

관련 집중 검사 75개와 Rust 라이브러리 **1,181개**, CLI **15개**, 전체 fmt·모든 target/feature의 Clippy가 통과했다. 기존 라이브러리 6개·CLI 1개의 opt-in 및 OS fixture 표시는 유지한다. 이후 실제 소스 10개 파일의 전체 바이트도 대조했다. 이 결과는 Windows 자동 검사이며 다른 OS의 실제 실행을 포함하지 않는다.

## 다운로드 완료의 적용 범위와 설정 보존

유효한 `iq4_nl` KV 캐시 설정이 프로젝트 내보내기·가져오기와 공통 설정 정규화에서 `f16`으로 바뀌던 문제를 고쳤다(`cea6707`). 중복된 8개 형식 목록 대신 기존 공통 9개 형식 목록을 사용한다. 알 수 없는 형식의 `f16` fallback과 K/V의 독립 처리는 유지한다. 실제 프로젝트·설정 로드 및 객체·함수형 patch 경로를 검사했다.

이전 다운로드가 완료됐을 때 현재 저장 폴더·저장소·런타임·모델·projector 선택을 덮어쓰지 않도록 시작 시점의 선택과 작업 소유권을 다시 확인한다(`f515274`). 확인 대화상자 안에서 사용자가 기다리는 동안 완료 알림이 사라져도 유효한 선택은 적용한다. 같은 시각에 새로 시작한 작업이나 이미 끝나 사라진 후속 작업과도 구분하며, 오래된 완료·취소 실패가 새 작업을 종료하지 않는다. 완료된 파일의 앱 전체 모델 목록 갱신과 소유한 작업의 종료 처리는 화면의 생존 여부와 별개로 보존한다. 마지막 두 경계는 실제 컴포넌트의 화면 제거·작업 교체 검사에서 실패를 재현한 뒤 재검증했다.

## 모델 다운로드의 중복 트리 조회 제거

GGUF와 동반 설정·토크나이저를 내려받을 때 같은 고정 revision의 저장소 트리를 두 번 조회하던 호출 경로를 정리했다(`5300d50`). 한 번 검증한 트리를 공통 파일 목록 변환과 동반 파일 계획에 함께 사용하고, 실제 전송 전에 전체 트리와 불필요한 목록을 해제한다. 전역 캐시를 추가하거나 revision·취소·페이지 검증을 생략하지 않는다.

해시 없는 기존 파일의 크기 기반 재사용은 기존 정책이다. 해당 경로가 검증된 출처를 기록한다는 정적 감사의 가정은 실제 코드와 맞지 않아 철회했다. 실제 새 전송 또는 공개된 digest 일치 때만 출처를 기록한다. 이 효율 개선에서 기존 파일을 덮어쓰거나 지원 파일의 다운로드를 일괄 거부하는 정책 변경은 하지 않는다.

합성 임시 폴더의 실제 Windows junction으로 외부 경로 거부·정상 링크·없어진 링크 대상을 검사했다. 제품 수정 전 **3개 성공·1개 실패**를 확인했고, 수정 후 관련 모듈 **34개**와 전체 Rust 라이브러리 **1,189개**, CLI **15개**, fmt·모든 target/feature의 Clippy가 통과했다. 이 조회 검사를 동시 경로 교체에 대한 원자적 파일 소유권 보장이나 Linux/macOS 실행 결과로 확대하지 않는다.

## 분할 모델 목록의 반복 파일 검사 제거

같은 분할 모델의 행마다 전체 조각을 다시 확인하던 비용을 줄였다(`4993294`). 한 번의 목록 조회 안에서 폴더·모델명·전체 조각 수·확장자가 같은 묶음의 누락 결과를 재사용한다. 다음 요청에서는 다시 검사하므로 새 파일과 삭제된 파일이 반영된다. 분할 파일명도 필요할 때 생성해, 단순 분할 모델 판정에 전체 이름 목록을 할당하지 않는다. 실제 다운로드 계획에는 기존 순서대로 전체 목록을 전달한다.

격리된 Windows 임시 폴더에 128개 조각을 가진 두 묶음을 만들고, 일부 누락·역순·중복을 포함한 **255행**을 실제 조회 함수로 세 번씩 측정했다. debug 빌드에서 수정 전 **1,398~1,476ms**, 수정 후 **23~28ms**였고 원래 경로를 상대 경로로 맞춘 반환값 전체의 SHA-256이 같았다. 이는 합성 로컬 파일 조회의 관찰값이며 실제 GUI·추론·원격 저장소 속도의 보장은 아니다. 시간 임계값을 추가하거나 검사 제한 시간을 늘리지 않았다.

회귀 검사는 서로 다른 폴더의 같은 이름, 조각 수·확장자가 다른 묶음, 요청 순서·중복·크기·경로, 다음 조회의 파일 추가·삭제를 확인한다. 관련 모듈 **44개**와 최종 Rust 라이브러리 **1,190개**, CLI **15개**, fmt·모든 target/feature의 Clippy가 통과했다. 기존 라이브러리 6개·CLI 1개의 opt-in 및 OS fixture 표시는 유지했다. 검사 전후 네이티브·도구 파일 15개의 바이트를 대조했고, 앞선 프런트엔드 16개 소스·7개 제어 파일과 설정 전체·프로필 7개·대화 8개도 보존됐다. 계측용 임시 검사는 배포 소스에 포함하지 않는다.

ZIP·tar의 직접 압축 해제와 릴리즈 압축 해제 모두에서, 작업 폴더 자체가 Windows junction이면 그 밖에 파일을 쓰던 문제를 합성 임시 폴더로 재현했다. 압축 해제를 시작하기 전에 실제 작업 폴더가 링크가 아닌 디렉터리인지 확인한다(`3a5d351`). 사용자가 선택한 상위 경로의 링크와 정상 작업 폴더에 동반 파일을 합치는 동작은 보존한다. 없는 작업 폴더는 기존 방식으로 생성한 뒤 다시 확인한다.

## 옵션 메타데이터와 프로필의 중복 작업

런타임 메타데이터를 적용할 때 전체 옵션과 기존 제약을 미리 복사하던 작업을 줄였다(`3b9f9ba`). 실제로 변경할 수 있는 옵션의 원본만 기록하고, 실패하면 해당 옵션을 복원하고 이번에 추가한 제약만 제거한다. 기존 소유권·중복 선언·비밀 표시·검증·오류 순서와 적용 실패 시의 정보 비공개 처리를 유지한다. 기존 제약과 새 자료형이 충돌하는 실제 공개 함수 검사로 전체 복원과 의도된 비밀 표시 보존을 확인했다. 이 검사는 원본·수정본 모두에서 통과했다.

실제 `apply`에 옵션 1,029개·제약 512개를 전달해 전후를 세 번씩 측정했다. 옵션 하나를 변경할 때 할당 요청은 **7,057회·5,910,534바이트 → 379회·4,254,586바이트**, 일치하는 옵션이 없을 때는 **7,059회·5,911,757바이트 → 375회·4,251,547바이트**였다. 각 경우의 옵션과 표시 결과 전체 해시는 같았고 반복 표본의 할당 수치도 같았다. 이는 누적 할당 요청량이며 peak 메모리·RSS·지연 시간 측정이 아니다. 계측용 allocator와 임시 검사는 최종 전체 검사 전에 제거했다.

프로필 갱신에서는 같은 변경 불가능 입력을 두 번 검증하던 호출 하나를 제거했다(`b51e7ee`). 최초 구조 검증과 삭제·기본 프로필 재지정·동일성·revision 경계 및 오류 순서는 유지한다. 기존 프로필 동작 검사는 최종 라이브러리 검사에 포함됐다. 호출 제거를 실제 저장 시간 개선 수치로 표현하지 않는다.

## 미디어 검증과 모델 설정 복원

임베딩 입력의 미디어를 검증하려고 전체 객체·문자열을 복사하고 임시 메시지를 만들던 경로를 원래 값의 참조 순회로 바꿨다(`b57f044`). 임베딩 전체의 합산 한도와 채팅 메시지마다 별도 한도, 원시 입력의 필터링·오류 순서·모델명 처리·입력 보존은 유지한다. 단일 객체·혼합 배열·다섯 번째 미디어 거부·여러 채팅 메시지·첫 오류 우선순위를 실제 요청 어댑터로 검사했다. 이 변경은 복사 경로 제거 근거이며 실제 엔진의 메모리나 추론 속도 측정이 아니다.

모델 설정을 복원할 때 새 키와 이전 llama.cpp 키를 서로 다른 저장소 조회에서 읽던 문제도 고쳤다(`589caa8`). 한 번의 복원 안에서는 필요할 때 한 번만 읽은 같은 결과를 사용한다. 실제 함수에서 두 번째 조회가 다른 저장 내용을 반환하도록 한 검사에서 수정 전 temperature·projector 복원이 실패했고 수정 후 통과했다. 현재 모델·적용된 프로필의 우선순위, 엔진별 키 분리, 허용 필드와 오류 전달은 보존하며 호출 사이의 캐시는 추가하지 않는다.

## MCP 도구 이름의 반복 충돌 처리

같은 이름의 도구가 반복되면 접미사를 매번 처음부터 검색하던 작업을 줄였다(`df2c76c`). 한 번의 이름 생성 호출 안에서 같은 기본 이름이 마지막으로 사용한 다음 번호부터 확인한다. 이미 접미사가 있는 이름·문자 정리·96자 절단·입력 순서와 최종 전체 이름의 중복 확인은 유지한다. 영구 캐시나 승인 정책 변경은 없다.

실제 원본·수정 함수의 합성 **86개 묶음·9,608개 항목**에서 반환 배열 전체와 직렬화 결과가 같았다. 같은 기본 이름이 3,000번 충돌하는 경우 집합 조회는 **4,501,500회 → 5,999회**였다. 접미사 자릿수가 바뀌는 경계와 서로 다른 기본 이름 사이의 충돌도 직접 검사했다. 합성 유틸리티의 관찰값이며 실제 MCP 서버·GUI 지연 시간이나 모든 이름 조합의 최악 비용을 보장하지 않는다.

최종 수정 후 Rust `1.98.0` 라이브러리 **1,195개**, CLI **15개**, fmt·모든 target/feature의 Clippy와 앱 타입 검사·전체 린트·production 빌드·기본 `npm test`가 통과했다. 기본 검사는 계약 패키지·provider 옵션·운영 스크립트·직접 Node 검사 및 **206개 파일·2,257개 Vitest 검사**를 포함한다. Coverage는 statements **84.13%**, branches **79.09%**, functions **82.40%**, lines **88.15%**이며 기존 기준을 유지한다. 기존 Rust 라이브러리 6개·CLI 1개의 ignored 표시도 유지했다. 전체 소스 795개와 제어 파일 7개의 검사 전후 해시, 네이티브 23개 전체 버퍼를 대조했고 설정 전체·프로필 7개·대화 8개 보존도 확인했다. 이번 결과에 새 실제 GUI·개인 엔진·후속 OS 검증은 포함하지 않는다.

세 subagent의 소스 검토와 원본·최종 바이트를 독립 확인해 상세 검토 기록을 갱신했다. 기록의 693개는 명시한 동작 경로의 검사이며 전체 파일·기능의 최적성 판정이 아니다. 92개는 상세 검토 대기, 10개는 첫 검토 단계다. IndexedDB 차단 후 늦은 연결 누수 의심은 현재 버전 인자로 발생할 수 있는지 다시 확인했다. 현재 호출은 기존 버전 또는 버전 1을 열며, [IndexedDB의 차단 알림은 더 높은 버전으로의 업그레이드 분기에서 발생한다](https://w3c.github.io/IndexedDB/#opening-a-database-connection). 합성으로 강제한 두 이벤트 순서를 현재 제품 결함으로 취급하지 않았으며, 실제 공개 이전 함수의 정상·오류 대조 네 경우와 구분해 기록했다.

## 남은 검토

아래는 아직 최종 구현·검증이 끝나지 않은 후보다. 반복된다는 이유만으로 기존 계약을 제거하지 않는다.

- 개인화 스킬의 반복 조회: 본문 복사는 줄였으며, 카탈로그와 선택한 스킬의 재확인 비용은 추가 검토 대상이다. metadata 뒤 본문 검증을 생략하거나 외부 수정·이름 우선순위의 freshness 경계를 합치지 않는다.
- 스냅샷 fingerprint와 런타임 크기·카탈로그의 디렉터리 탐색: 일부 탐색 비용은 합성 proxy에서 관찰했지만 실제 전체 경로의 측정이 더 필요하다. 변조 전후 fingerprint를 합치거나 경로만으로 캐시하지 않는다.
- native 벤치마크 이력의 다른 호출 경로와 나머지 기능·도구 및 OS별 분기는 추가 상세 검토 대상이다. N09의 helper 측정을 전체 이력 API 지연 시간으로 취급하지 않는다.
- 자원 추정의 추가 호출 경로도 검토를 이어간다. N10의 캐시 교체 개선은 실제 사용자 모델·OS I/O·RSS 검증을 대신하지 않는다.
- 발행 요청의 저장 전후 직렬화 재사용은 추가 검토 대상이다. P02에서 호출자의 중복 1회를 줄였으며, 나머지 저장·native 바인딩·재시도 경계는 임의로 합치지 않는다.
- 어댑터의 모델 검사·manifest 조회·시작 자원 복구·명령 layout 검증에는 반복 호출 후보가 남아 있다. 실제 호출 빈도와 파일 변경·검증 경계를 측정한 뒤 판단하며, 공개 helper나 독립 검증을 단순 중복으로 삭제하지 않는다.
- 플랫폼 소스 감사의 설치 파일 조회와 archive 작업 폴더 경계는 위의 Windows junction 검사로 재현·수정했다. updater 상태와 실제 검증 가능 여부, OS별 안정적인 장치 식별자 후보는 추가 조사 대상이다. 합성 경계 검사와 실제 OS 조건을 구분하고, 아직 실행으로 재현하지 않은 후보를 확정된 제품 결함이나 검증 성공으로 기록하지 않는다.
- 공통 옵션의 도움말 줄 수를 사실·출처마다 다시 세는 경로와 옵션 가져오기의 하위 명령 범위·명시적 false 별칭 처리는 새 검증 후보로 남아 있다. 실제 공개 함수용 재현 코드는 준비했지만 아직 삽입·실행하지 않았으며, 기존 전체 검사 성공으로 새 경우가 통과했다고 표시하지 않는다.
- 자동 검증 취소 후의 결과 저장·같은 요청 안의 runtime identity 중복 조회와 모델 그룹 구성 중 취소 확인도 추가 검증 대상이다. 취소·재시도·다음 호출의 freshness·기존 캐시 및 출력 계약을 지키는 공개 경로 검사를 먼저 실행한다.
- 실제 앱·추론·pointer drag 및 나머지 기능·도구·OS별 흐름 검토는 남아 있다. 이번의 격리된 화면 검사와 자동 검사 성공을 프로젝트 전체 완료로 취급하지 않는다.

이미 존재하는 경계·인증·프로세스 소유권·취소·변조 검출·데이터 이전을 비용이라는 이유로 제거하지 않는다. 채팅은 현재 idle 단계에서 이력을 저장하므로, 매 스트리밍 토큰마다 저장한다는 가정은 실제 호출 경로와 맞지 않았다. 실제 Linux/macOS 실행은 이번 Windows 검사의 성공으로 표시하지 않는다.

원본 감사·합성 측정·실패 재현·진행 상태는 `tmp/efficiency-review/`에 보관하고 커밋하지 않는다.

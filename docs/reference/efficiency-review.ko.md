# 프로젝트 효율 검토 기록

전체 코드의 반복 검토와 개선을 진행 중이다. 아래 결과는 완료한 항목의 근거이며, 프로젝트 전체의 검토나 최적화가 끝났다는 판정이 아니다. 시작 소스는 `08c0916`이다.

이는 합성 변환 함수의 측정이며 GUI 전체 지연 시간이나 실제 엔진 추론 속도를 뜻하지 않는다. 실행 환경과 다른 작업의 부하에 따라 절대 시간은 달라진다. F01은 시간 임계치 대신 실제 전체 라이브러리 복사 횟수로 회귀를 검사한다.

F01/F02 이후 UI **201개 파일·2,189개 테스트**, 관련 프로필 검사 161개, 직접 검사·i18n·typecheck·production 프런트엔드 build가 통과했다. 전체 lint는 오류 0개이며 기존 `CustomSelect` effect 의존성 경고 1개가 있다. jsdom의 canvas/pseudo-element 안내와 큰 workbook 청크 안내도 유지한다. 검사 기준·timeout·실패 제외는 변경하지 않았다.

Windows 개발 창에서 Strata의 런타임 → 프로필 → 옵션 화면을 열었다. native SSE 수정 후 다시 열린 개발 창에서는 llama.cpp의 성능 필드에 컨텍스트 `8192`를 입력하고, 변경 버리기를 거쳐 닫았다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시는 시작 전과 같았다. 저장·초기화·실제 추론은 실행하지 않았다.

F03의 32개 검색어·문서 4개 합성 비교에서, 각 64 KiB 문서의 전체 순위 계산은 7.37→5.87 ms, 각 1 MiB 문서는 113.51→90.97 ms였다. 이어서 컨텍스트에 들어가지 않는 나머지 첨부 계산을 없앤 효과를 별도로 측정했다. 같은 컨텍스트를 만드는 비용은 각각 5.71→1.47 ms, 90.72→22.64 ms였다. 단계별 기준을 섞어 비율을 계산하지 않으며, 문서 선택·순서·전달 내용을 바꾸지 않았다.

추가 독립 교차 검토에서 프로필 메모·옵션 별칭·문서 검색의 관련 검사를 통과했다. 문서 검색은 시작 소스와 수정 소스를 동일 입력으로 비교한 순위 100건·컨텍스트 800건에서도 결과가 같았다. Unicode와 첨부 이름, 0·음수·비유한 예산을 포함해 기존 동작의 보존을 확인했다.

## Responses 이력 공유

N02는 각 응답에 전체 누적 메시지를 복사해 보관하던 구조를 부모 이력과 이번 요청의 메시지를 공유하는 구조로 바꿨다. 새 요청을 보낼 때만 전체 메시지 배열을 만들고, 잠금 안에서는 이력의 공유 참조만 가져온다. 공개 응답 JSON과 128개 응답 조회 한도, 기존 임의 퇴출 정책은 유지한다. 상위 응답을 삭제·취소하거나 퇴출해도 남아 있는 하위 응답은 기존 전체 대화를 이어갈 수 있다. 구현 커밋은 `ac36b85`다.

실제 loopback 검사에서 stream/non-stream 연속 요청의 전달 메시지, 상위 응답 삭제·취소, 다른 세션과 개인 upstream 인증, 퇴출 후 하위 응답의 계속 사용을 확인했다. 깊이 8,192 이력의 해제와 공유된 깊이 512 이력을 여러 소유자가 동시에 해제하는 합성 검사도 통과했다. 이는 운영 환경의 충돌을 재현했다는 뜻이 아니다.

합성 payload 비용 모델에서 64 KiB 메시지를 사용하는 깊이 128 이력의 보관량은 1,082,634,048→16,785,024바이트였다. 별도 계수 allocator로 측정한 합성 `String`/`Vec`/`Arc` 이력은 작은 메시지 깊이 128에서 1,576,032→25,600바이트, 큰 메시지 깊이 16에서 17,837,792→2,098,816바이트였다. 공개 응답·HTTP·`serde_json::Value`의 실제 비용이나 OS RSS를 측정한 수치로 확대하지 않는다.

최종 N02 소스에서 gateway **83개**, 독립 전체 Rust 라이브러리 **1,148개** 검사가 통과했고 기존 opt-in/fixture ignored 6개는 남아 있다. pinned Rust의 전체 target·feature Clippy도 경고를 오류로 처리해 통과했다. 전체 `cargo test` 시도는 병렬 빌드 중 Windows 페이징 파일 부족과 실행 중인 개발 GUI의 실행 파일 잠금으로 실패했다. 빌드 작업을 1개로 제한한 라이브러리 재검사는 통과했으며, 전체 실행을 통과했다고 기록하지 않는다. 시스템 페이징 설정·의존성·검사 제외 조건은 변경하지 않았다.

회귀 검사는 세 가지 비정상 값을 최상위와 파일 항목에 각각 넣은 6개 사례의 실제 수정 전 실패를 기록한 뒤 수정 후 통과했다. 유효한 추가 정보 3개와 다른 저장소·revision 필터도 전체 반환값으로 비교한다. 비교 과정에서 이전 테스트 바이너리가 재사용된 자료와 Windows 경로 표기가 달라 생긴 실패는 제외했다. 올바른 입력·같은 경로·별도 빌드 구분값·실행 파일 해시·실제 호출 계수로 결함 재현을 확인했으며, 비교를 통과시키기 위해 반환 필드를 제거하지 않았다.

최종 관련 검사 22개·Rust 라이브러리 1,159개·CLI 15개·fmt·전체 target/feature Clippy가 통과했고 기존 ignored 6개·1개는 유지한다. 현재 Cargo 산출물에 원본 `runtime_adapter_setup`·`runtime_adapters` 소스를 직접 컴파일한 통합 검사 2개도 통과했다. 이 직접 실행은 전체 Cargo 통합 검사 성공과 구분한다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시도 같다. 합성 Windows 검사이며 새로운 실제 모델 추론·GUI·다른 OS 검증이나 성능 개선을 입증한 결과로 확대하지 않는다.

## Python 내보내기와 보조 도구 검토

T01은 pinned `mlx-lm` wheel을 만들 때 이미 읽은 파일을 `RECORD`용으로 다시 해시하고, 파일마다 전체 크기를 다시 합산하던 작업을 줄였다. 같은 immutable 바이트의 raw digest 하나로 source record와 `RECORD`를 만들며, 중복 canonical 파일명은 기존 값을 뺀 크기와 마지막 내용을 사용한다. 변경된 파일을 탐지하는 앞선 source-record 재검증은 유지한다. 구현 커밋은 `3e2d23c`다.

합성 101개 파일의 실제 원본·수정 script 비교에서 direct URL 경로의 SHA-256 호출은 203→102회, source-record fallback은 304→203회였다. 누적 합산은 102회·5,252개 항목 재순회에서 증분 계산으로 바뀌었다. 읽기 횟수와 wheel member 내용·순서, source JSON·RECORD 해시는 같았다. 이는 실제 엔진의 내보내기 시간·RSS 측정이 아니다. portable 검사 8개를 포함한 provider 검사 20개와 별도 provider 검사 5개, runtime-adapter 12개·model-repair 5개가 통과했다. 64MiB·256MiB 경계는 작은 파일에 통제된 크기를 적용했고, 10,000개 항목은 같은 빈 파일을 서로 다른 이름으로 매핑했다. 이 경계 검사를 대용량 실제 I/O 검사로 표시하지 않는다. 기존 실제 ZIP·offline pip 임시 설치·재캡처·변조 거부 검사는 유지했다.

T02는 runtime의 버전·도움말 출력을 전부 보관한 다음 잘라내던 수집기를 바꿨다. stdout·stderr 각각 최대 65,536자를 보관하면서 끝까지 읽고 디코딩한다. stdout 우선 반환·활성 locale·개행 변환·원래 비정상 종료 오류 우선순위와 15초 제한을 유지한다. 한도 뒤의 잘못된 인코딩도 거부하며, 하위 프로세스가 pipe를 계속 잡고 있어도 수집 제한을 지킨다. Windows native 오류는 원래 Win32 코드와 설명으로 전달한다. 구현 커밋은 `58bc9b5`다.

같은 합성 child가 각 stream에 8MiB씩 출력하는 원본·수정 helper를 별도 프로세스에서 각 3회 비교했다. 여섯 번 모두 반환 65,536자의 해시가 같았고, 최종 수집기도 전체 16MiB를 읽었다. Python 할당 최고치 중앙값은 33,630,277→289,186바이트, 1ms 간격으로 관측한 working-set 증가량 중앙값은 16,969,728→479,232바이트였다. 측정 프로세스에는 관측 thread 비용이 포함되며, 샘플은 실제 최고치를 보장하지 않는다. 수집 시간 중앙값은 0.250→0.422초로 늘었다. 이 결과를 GUI·실제 엔진·모델·GPU 메모리나 전체 속도의 개선으로 해석하지 않는다.

최종 Python runtime-adapter 검사 21개가 통과했다. 대량 출력·Unicode 문자 제한·개행·한도 뒤 디코딩 오류·비정상 종료·시간 제한과 direct child 정리를 포함한다. 최종 native `--lib --bins --examples`도 라이브러리 1,158개·CLI 15개와 다른 binary·예제 test target 빌드를 통과했고 기존 ignored 6개·1개는 유지한다. integration을 포함한 Cargo 실행은 실행 중인 개발 GUI의 파일 잠금으로 실패했다. GUI를 종료하지 않고, Cargo로 최신 라이브러리와 fixture만 빌드한 뒤 원본 `runtime_adapter_setup`·`runtime_adapters` 테스트 소스를 해당 산출물에 직접 컴파일해 실행한 두 검사는 통과했다. 이 직접 실행을 전체 `cargo test` 성공으로 기록하지 않는다. 설정 파일 전체·프로필 7개·대화 파일 8개의 해시도 같다. Linux/macOS의 실제 출력 수집 검사는 수행하지 않았다.

T03은 Strata 준비와 모델 미선택 probe에서 같은 설정의 JSON 해석·정책 검증을 2회에서 1회로 줄였다(`b8c9e4e`). 두 번째 원문 읽기와 실행 파일·tokenizer 존재 확인은 유지한다. 다른 모델 설정을 지정한 probe는 계속 두 설정을 각각 검증하고 native build를 비교한다. 사용하지 않게 된 내부 JSON 래퍼와 setup의 설정 지역 변수도 제거했다. CLI·manifest·draft·모델·옵션·argv·artifact 순서는 유지하며, 출력 수집 코드는 바꾸지 않았다.

실제 준비·probe 함수의 합성 비교에서 정상 출력·오류 10개 사례가 같았다. 약 360바이트 설정과 인자 1,000개를 넣은 약 19KiB 설정 모두 읽기·파일 확인·하위 명령 실행 횟수는 같고 JSON 해석만 줄었다. 준비 도중 설정 파일을 교체하면 예전 구현은 서로 다른 시점의 정보를 섞어 반환할 수 있었다. 수정 후에는 원문 차이를 감지해 거부한다. 최초 검증 후 실행 파일이나 tokenizer가 사라지는 경우도 실제 임시 파일로 재현해 후속 동작 전에 실패하는지 확인했다.

최종 Python runtime-adapter 검사 27개와 구문 검사가 통과했다. 독립 검증은 보관된 정규화 JSON의 해시와 전체 결과를 다시 계산하고, 다른 모델의 별도 검증 및 출력 수집 코드의 바이트 보존도 확인했다. Git revision만 고정한 fixture를 사용했으며, 도움말용 합성 모듈과 Python 버전 명령은 실제 subprocess로 실행했다. 실제 Strata 추론·사용자 모델·다른 OS 실행이나 지연 시간·RSS 개선을 입증한 결과는 아니다.

Python helper와 플랫폼 보조 스크립트는 실제 embedded 호출·CI·운영자 도구로 연결돼 있어 미사용으로 삭제하지 않았다. 검증 시점이 다른 읽기는 임의로 합치지 않는다.

T04는 compatibility wheel을 읽을 때 각 파일의 ZIP metadata를 얕게 복사하던 코드를 제거했다(`a37c415`). 출력은 별도의 새 metadata를 구성하므로 입력 descriptor를 다시 복사할 필요가 없었다. 실제 전체 `build_wheel` 함수의 합성 101개 파일 비교에서 복사는 101회→0회였으며, 출력 ZIP 바이트·audit·파일 순서·내용·속성·라이선스·RECORD는 같았다. 관련 Python 15개 검사도 통과했다. source 준비의 재해시는 출처·변조 검증에 필요해 유지했고, 실제 upstream wheel·설치·다른 OS 실행이나 시간 개선을 입증한 결과는 아니다.

같은 변경의 후속 해시 캐시 후보는 채택하지 않았다. 101·1,000개 파일과 세 가지 패치 크기의 전체 wheel 생성 호출을 순서를 교대해 각각 12회 측정했다. 여섯 조합 중 네 조합의 중앙값은 늘었고, 두 조합의 감소는 1% 미만이며 측정 범위가 겹쳤다. 모든 파일에 추가되는 조회와 코드 복잡성을 정당화할 이점이 확인되지 않아, 검증된 ZIP 복사 제거만 유지했다. 반환 결과가 같거나 해시 호출 한 번이 줄었다는 사실만으로 더 효율적이라고 판정하지 않았다.

빌드·패키징 helper 다섯 개도 package script·workflow·플랫폼 분기·운영 문서까지 추적했다. 이 파일들에서 삭제할 미사용 내부 코드는 확인하지 못했다. 대신 Linux release의 사전 검사와 `package:tauri`가 CLI release 빌드를 두 번 호출하는 것을 확인해, 중간 검사에서 사용하지 않는 앞선 호출 한 줄을 제거했다(`24efa45`). CLI 빌드 → frontend 빌드 → GUI packaging 순서와 path remap·fixture 제외·모든 검사·다른 OS의 명령은 유지한다. 기존 YAML parser를 통한 workflow 판독·명령 보존 확인과 Node packaging 검사 3개가 통과했다. 실제 Linux CI·패키지 생성·설치는 실행하지 않았으며 빌드 시간 개선을 측정한 결과도 아니다.

## 플랫폼 검증 도구의 중복 작업

T05는 읽기 전용 DMG의 같은 앱 서명 정보를 인접한 두 assertion에서 각각 조회하던 호출을 한 번으로 줄였다(`40551e1`). 엄격한 서명 검증과 GUI·CLI 바이너리의 개별 조회는 유지한다. 전체 파일이 이 변경만 포함하는지 확인하고 실제 변경 소스 블록의 정상·오류 8개 사례를 비교했다. 해당 블록의 조회는 4회에서 3회로 줄었으며 Node 구문·린트 검사가 통과했다. 실제 macOS의 DMG·codesign·Swift·GUI 검사는 실행하지 않았고 시간·RSS 개선을 측정한 결과도 아니다.

T06은 Windows PR runtime 패키징에서 같은 디렉터리 이름을 DLL마다 다시 계산하던 작업을 디렉터리마다 한 번으로 줄였다. 명시된 브랜치 이름이 있으면 사용하지 않는 Git fallback 조회도 생략한다(`f6c7611`). 비어 있거나 공백인 이름의 fallback·오류 처리, CRT 탐색·System32 필터·복사 순서·파일 해시·출처·manifest 정렬은 유지한다. 실제 workflow의 repository는 PR head 저장소이고 URL은 기준 upstream의 PR을 가리키므로 이 계약도 보존한다.

전체 PowerShell 소스를 합성 Unicode·공백 경로와 복수 CRT 디렉터리에서 실행한 12개 변형은 정상 패키지 8개와 의도한 오류 4개를 확인했다. 추출한 ZIP 항목의 순서·이름·크기·내용 해시, 출처·manifest 본문, 복사된 바이트·속성과 오류가 같다. 관련 경로 계산은 17회→4회, 명시된 브랜치의 Git 조회는 1회→0회다. ZIP 생성 시각에 따른 전체 archive 바이트 차이와 실제 MSVC 환경·CI·발행·추론은 이 결과에 포함하지 않는다.

Linux 런처 등록의 재판독을 합치는 후보는 철회했다. 첫 관찰 이후 새 AppImage 런처가 생성되거나 기존 항목을 교체하면 후보가 이를 개발용 항목으로 덮어쓰는 두 사례가 실제로 재현됐다. 운영 코드를 원래 바이트로 복원하고 임시 파일시스템에서 전체 등록 함수를 호출하는 회귀 검사 두 개를 추가했다(`cec0a8a`). 후보에서는 두 검사가 실패했고 복원 후 8개 통과·기존 GIO 검사 1개 skip이다. 이것은 일반적인 원자적 등록이나 실제 Linux 데스크톱 검증을 입증하지 않는다.

runtime smoke·플랫폼 검증·설치 도구 15개는 실제 호출과 데이터 흐름을 추가 검토했다. readiness·취소·프로세스 정리·설치 전후 관찰은 각각 필요해 제거하지 않았다. provider runtime의 Node 검사 40개와 합성 self-test도 통과했다. 실제 엔진·설치·Linux/macOS 실행은 이 합성·정적 검사의 성공과 구분하며, [플랫폼 검증 안내](cross-platform-validation.md)와 각 OS 인계의 기존 명령을 유지한다.

## 공통 API·설정 참조 감사

native 공유 응답의 오류 생성에서 양쪽 값이 같은 조건식과 같은 서비스 코드를 다시 대입하는 분기를 제거했다(`b2e91e9`). HTTP 오류 종류·메시지·재시도 여부·상태·Retry-After·서비스 코드, 정상 응답과 receipt 검증은 그대로다. API 관련 8개 파일·48개 검사, 발행 화면 연계 2개 파일·21개 검사와 별도 공유 전송·제어기 3개 파일·19개 검사가 통과했다. 겹치는 검사는 합산하지 않는다.

## 공통 화면과 실행 옵션의 반복 작업

세션 polling 훅에서 렌더마다 만들던 콜백 보관 객체를 두 개의 지속적인 ref로 바꿨다(`a077d5c`). 최신 콜백 전달과 기존 구독의 수명은 유지한다. 반면 Flash 메시지의 내부 함수에 memo hook을 추가하는 후보는 실제로 함수 표현식 생성을 줄이지 못해 철회했다.

선택 메뉴는 바뀌지 않은 라벨에 이벤트를 매번 다시 연결하는 작업과 강조 항목 이동 때의 불필요한 크기 측정을 줄였다(`34cc008`). 선택지나 글꼴 때문에 실제 크기가 바뀌면 다시 배치하고, `ResizeObserver`가 없는 환경에는 렌더마다 확인하는 기존 호환 경로를 유지한다. 상태 갱신에는 최종 화면 경계 보정값을 비교하며, DOM 측정은 갱신 함수 밖에서 수행한다. 전체 옵션을 매 렌더 문자열로 만드는 후보와 갱신용 ref 카운터는 제외했다. 옵션 직접 입력의 검색어 소문자 변환도 옵션마다 반복하지 않는다.

## Windows 프로세스 종료 확인

Windows의 job 통계가 0이 된 뒤에도 독립적으로 보관한 하위 프로세스 핸들이 아직 종료 신호를 보내지 않은 실패를 재현했다. job 핸들을 직접 기다리는 후보도 반복 검사에서는 통과했지만, [Microsoft의 job 신호 설명](https://devblogs.microsoft.com/oldnewthing/20130405-00/?p=4743)은 시간 제한 종료의 신호를 설명하므로 일반적인 명시적 종료 완료 계약으로 채택하지 않았다. 최종 수정은 실제 job 멤버의 프로세스 핸들을 보관하고 종료 신호를 확인한다(`d0d04e1`).

멤버 목록은 크기 부족과 부분 반환을 처리하는 제한된 조회로 수집한다. 시작 직후와 종료 요청 전에 핸들을 보관해 PID 재사용을 구분하고, 조회·핸들 확보가 불확실하면 정리 완료를 보고하지 않는다. 기다린 뒤 목록과 모든 보관 핸들의 신호를 하나의 짧은 잠금에서 재확인한다. 막히는 대기 동안은 잠금을 잡지 않는다. Win32 오류는 [공식 오류 조회 계약](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-getlasterror)에 따라 시계를 다시 읽기 전에 보존한다. 중복 멤버 확인 helper와 별도의 0초 관찰 인자는 제거했다.

실행 중인 트리의 0초 확인은 거부하고 이미 종료를 관찰한 트리는 즉시 확인할 수 있도록 검사했다. 부모가 먼저 종료한 뒤 남은 하위 프로세스, 실제 복수 멤버 조회, 취소·등록 해제·소유권을 넘긴 프로세스도 관련 검사에 포함한다. 원래 실패 검사의 대기·경과 시간 조건은 유지하며, 잘못된 Unix 조건부 경계는 커밋 전에 복구했다. 최종 집중 검사 13개와 전체 Rust 라이브러리 **1,162개**, CLI **15개**, 전체 fmt와 모든 target·feature의 Clippy가 통과했다. 라이브러리 6개·CLI 1개의 기존 opt-in 및 하위 프로세스 fixture 표시는 유지하고 새로운 skip은 추가하지 않았다.

범위는 Windows에서 실행한 합성 프로세스 및 자동 검사다. Linux 교차 검사는 외부 libdbus·Wayland의 pkg-config 설정에서 중단되어 앱의 Linux 빌드 성공으로 기록하지 않는다. Unix 알고리즘·공개 API·기본 설정·의존성·lockfile은 보존하며 Linux/Mac 기기에서의 빌드·소유 프로세스 종료·취소·headless 유지 동작 확인은 후속 작업이다. 전체 설정·프로필 7개·대화 8개 파일 해시는 최종 검사 뒤에도 같다. 이번 검사로 소스 폴더에 새로 생긴 Python bytecode는 없었으며, 원래 임시 자료와 사용자 데이터를 정리 대상으로 삭제하지 않았다.

## 남은 검토

아래는 아직 최종 구현·검증이 끝나지 않은 후보다. 반복된다는 이유만으로 기존 계약을 제거하지 않는다.

- 개인화 스킬의 반복 조회: 본문 복사는 줄였으며, 카탈로그와 선택한 스킬의 재확인 비용은 추가 검토 대상이다. metadata 뒤 본문 검증을 생략하거나 외부 수정·이름 우선순위의 freshness 경계를 합치지 않는다.
- 스냅샷 fingerprint와 런타임 크기·카탈로그의 디렉터리 탐색: 일부 탐색 비용은 합성 proxy에서 관찰했지만 실제 전체 경로의 측정이 더 필요하다. 변조 전후 fingerprint를 합치거나 경로만으로 캐시하지 않는다.
- native 벤치마크 이력의 다른 호출 경로와 나머지 기능·도구 및 OS별 분기는 추가 상세 검토 대상이다. N09의 helper 측정을 전체 이력 API 지연 시간으로 취급하지 않는다.
- 자원 추정의 추가 호출 경로도 검토를 이어간다. N10의 캐시 교체 개선은 실제 사용자 모델·OS I/O·RSS 검증을 대신하지 않는다.
- 발행 요청의 저장 전후 직렬화 재사용은 추가 검토 대상이다. P02에서 호출자의 중복 1회를 줄였으며, 나머지 저장·native 바인딩·재시도 경계는 임의로 합치지 않는다.

이미 존재하는 경계·인증·프로세스 소유권·취소·변조 검출·데이터 이전을 비용이라는 이유로 제거하지 않는다. 채팅은 현재 idle 단계에서 이력을 저장하므로, 매 스트리밍 토큰마다 저장한다는 가정은 실제 호출 경로와 맞지 않았다. 실제 Linux/macOS 실행은 이번 Windows 검사의 성공으로 표시하지 않는다.

원본 감사·합성 측정·실패 재현·진행 상태는 `tmp/efficiency-review/`에 보관하고 커밋하지 않는다.
